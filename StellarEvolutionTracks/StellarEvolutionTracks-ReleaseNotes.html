A. Release Status

Version 1.7.0 is the result of a second, independent review series. The first series (Kickoff through Audit4) closed at version 1.5.0 with no open finding from any reviewer. The second series began at Kickoff2 on 19 September 2026, when the Help was rewritten as the Beats tutorial (eleven short arguments, each a command whose figure is the evidence, with the equations placed after the figure that earns them) and the Help tests were made layout-aware; the four program modules did not change. Three audit rounds followed, each with Codex, Grok and Copilot: Audit21 (repaired as 1.6.0), Audit22 (repaired as 1.7.0) and Audit23, which reviewed 1.7.0 and produced no code change.

Audit21 and Audit22 together raised 43 findings: 38 repaired, 4 repaired in part, 1 accepted with no change needed, none declined. The developer found two further sets of defects that no reviewer had named, and repaired them: the Chandrasekhar-limit coefficient (typed 5.836, derived 5.825, so MCh(μe = 2) is 1.4563 and not 1.459), and three validation gaps that the boolean-refusal matrix exposed. Independent reviews of each round’s diff before delivery found 6 and 5 further problems, all fixed.

Audit23 verdicts on 1.7.0.
  • Codex: “NOT READY for release as 1.7.0.” No P1; two P2 (KB-1, KB-2) and one P3 (KB-3), each reproduced by its author against the delivered tree and each reproduced again by the developer for these notes. Its own run: 309 tests, OK, 217 s.
  • Grok: “I would give this build to students.” No P1 or P2; one P3, a documentation gap (KB-4). 309 tests, OK, 241 s.
  • Copilot: no release-blocking defect, no numbered findings; overall confidence High.

Status of this release. The six delivered files are byte-identical to the Response-to-Audit22 package (SHA-256 manifest in Part G, checked for these notes). The Audit23 defects are therefore open: they are documented here, with reproductions and workarounds, and their repair is deferred to a later maintenance round. This is the project owner’s decision, taken so that conversion of the remaining programs’ Help files to the Beats format can continue; it is not a claim that the defects are unimportant. Codex regards KB-1 and KB-2 as release-relevant, and the notes say so plainly.

What a student can rely on. The defaults and every command in the Help and in the SampleOutputs guide are unaffected: the maximum-mass models of the sample neutron-star runs (the default polytrope, Γ = 3.0 with pnuc = 0.04, pnuc = 0.08 and the ideal neutron gas) change by less than 0.0001 per cent when the surface cutoff is tightened from 10−8 to 10−10, and none of the eleven sample runs sets --rho_lo above the default. The defects bite when a run leaves the documented path: a soft polytrope (Γ below about 1.5) with a large --p_nuc, or a --rho_lo raised past the point where the mass has already begun to fall.

Design decisions confirmed in Audit23

  • The 4/3 polytrope bound. Codex: “refusing Γ ≤ 4/3 is a scientifically defensible and pedagogically clearer choice than merely refusing Γ ≤ 6/5”; the source now distinguishes finite radius, Newtonian radial stability and causality, consistently across the command line, the code and the Help. Grok agrees and asks only for the one-sentence caveat in KB-4.
  • The Mestel matching composition. The disclosed convention (the degeneracy boundary is envelope material) was “propagated consistently through the source docstrings, terminal summary, Help derivation, caveat, and EXP-16”, and the fifth-power consequence of the alternative is made explicit; Codex judged that this “satisfies the prior request to state and test the modeling assumption”.
  • The --mu_e option name. No reviewer asked for it to be renamed --mu_e_core. It is unchanged. (The rename would break every existing command line and direct caller; it remains available as a separate round on request.)

KB-1 — The polytrope surface cutoff is not bounded by the quoted 0.1–0.6 per cent

What happens
A polytrope’s density reaches zero only slowly, so the integrator stops when the density has fallen to y_floor = 10−8 of its central value. The 1.7.0 warning (printed only for Γ < 1.4) and the Help say that tightening the cutoff to 10−10 would lengthen the radius by roughly 0.1 to 0.6 per cent. Those figures were measured for one Newtonian model (pnuc = 0.04, one density). For TOV models the effect depends on pnuc and on the central density as well, and is far larger.
Measured

1.401.06.768 × 10171172.544 km1257.492 km7.245 %none (this is the Mmax model of a default sequence: 29.1967 M☉, turning point found, causal)
1.391.05.771 × 10171417.557 km1545.891 km9.053 %says 0.1–0.6 %
1.501.02.84 × 1018285.490 km288.548 km1.071 %none
The radius reported is always the smaller one: the cutoff radius understates the star.
Reproduce
import physics_sev as P
eos = P.PolytropeEOS(gamma=1.40, p_nuc=1.0)
yc = eos.x_from_density(6.768e17)
for yf in (1e-8, 1e-10):
    M, R, _ = P.integrate_structure(eos, yc, relativistic=True, r_scale=1.5e4, y_floor=yf)
    print(yf, M / P.M_sun, R / 1e3)
# 1e-08 29.1967 1172.544
# 1e-10 29.1984 1257.492
Who is affected
Anyone running --mode nsmr --eos polytrope with Γ below about 1.5 and a --p_nuc well above the default 0.04. y_floor is an argument of integrate_structure only; it is not exposed by ns_mass_radius_curve or the command line. The sample runs and the Help’s commands are not affected: the radius of every maximum-mass sample model changes by less than 0.0001 per cent.
Workaround
Treat every polytrope radius at Γ below about 1.5 as a lower bound (a cutoff radius), and do not read causality plus Γ ≥ 1.4 as a numerical trust test. For a single model, call integrate_structure with y_floor=1e-10, as above, and compare.
Statements it contradicts
Beat 9 (the paragraph quoting 0.1–0.6 per cent); the Domain-of-Validity row “reasonably represented … Γ of at least about 1.4”; the POLYTROPE_GAMMA_SLOW_SURFACE warning text in physics_sev.py.
Suggested repair (not implemented)
Codex offers three: converge each polytrope surface adaptively; rerun the extremum (preferably every plotted model) at a tighter cutoff, report the measured change and warn above a stated tolerance; or expose y_floor and label all polytrope radii plainly as cutoff radii, with no parameter-independent percentage. Whichever is chosen, the Help, source docstring, terminal warning, validity table and these notes change together, with TOV tests spanning Γ near 1.4, pnuc from the default to 1, and central density.

KB-2 — A maximum at the lowest sampled density can print a false “causal” verdict

What happens
The causality scan is meant to cover the whole stable branch, or the whole sampled branch when no turning point exists. The code always builds the branch by walking down from the index of the maximum mass. When the mass is already falling at --rho_lo that index is the first model, so the scan covers one model and every higher density is left out. The summary correctly reports that no turning point was found, but still prints causal = True and calls the one-point value the peak “on the branch”.
Reproduce
import physics_sev as P
r = P.ns_mass_radius_curve(eos_name="polytrope", gamma=2.5, p_nuc=0.04, n=20,
                           rho_lo=2e18, rho_hi=1e19, relativistic=True)
s = r["summary"]
print(r["i_max"], s["turning_point"], s["stable_branch"], s["causal"],
      s["cs_over_c_at_Mmax"], s["cs_over_c_max_branch"])
# 0 False False True 0.9274 0.9274
An independent scan of the same equation of state over the 20 returned densities finds a maximum cs/c of 1.185920, with 16 of the 20 models acausal. The command line prints “Largest sampled mass … (NOT a maximum)” and “0.9274 there, 0.9274 peak on the branch”, with no *** ACAUSAL *** flag; the plot annotation and the CSV provenance repeat the 0.9274.
Who is affected
A run whose --rho_lo is raised until the mass is falling at the first model (the default --rho_lo is 1017 kg m−3). Codex notes the same question is open for a maximum at --rho_hi and beside a convergence gap: no test asserts causality in any of the three “no resolved turning point” cases.
Workaround
Trust the causality verdict only when the summary reports a turning point, that is, when the mass line reads “Maximum mass” and not “Largest sampled mass … (NOT a maximum)”. If it does not, lower --rho_lo until the mass is rising at the first model.
Statements it contradicts
The Validity table’s “whole branch” row, and the known-artefacts bullet saying the scan runs from the lowest sampled model to the maximum-mass model.
Suggested repair (not implemented)
Codex separates two questions the single causal field conflates: did any converged sampled model violate cs ≤ c, and was a physically classified stable branch fully sampled, and causal? For a maximum at rho_lo the stable branch has not been sampled, so its causality is unknown, not True, while the sampled-range diagnostic still scans every converged row. Add boundary and gap tests covering the terminal, plot annotation, summary fields, warnings and CSV provenance, and a Help caveat that distinguishes “sampled range” from “resolved stable branch”.

KB-3 — turnoff_mass() does not validate its paired arrays

What happens
Unequal lengths are silently truncated by zip; an invalid mass row is silently discarded; non-numeric entries raise a raw TypeError; duplicate lifetimes give an ambiguous interpolation.
Reproduce
turnoff_mass([1, 2, 3],   [10, 5],     7)   # 1.4285714285714288  (third mass dropped)
turnoff_mass([-1, 1, 2],  [20, 10, 5], 7)   # 1.4285714285714288  (negative mass dropped)
turnoff_mass(["1", "2"],  [10, 5],     7)   # TypeError, not ValueError
turnoff_mass([1, 2, 3],   [10, 10, 5], 10)  # 2.0  (two masses share a lifetime)
Who is affected
Direct callers of the public function only. The HR mode builds clean, equal-length arrays itself, so no command-line result is affected. It matters because the 1.7.0 release claims a swept public numeric API. None lifetimes have a legitimate meaning (a track did not reach the TAMS) and stay filtered.
Workaround
Pass equal-length lists of finite positive numbers with distinct lifetimes.
Suggested repair (not implemented)
Require equal lengths; validate each mass with the common finite-positive helper and each lifetime as None or finite positive; require the retained relation to be single-valued and ordered (or define and test tie handling); raise ValueError throughout; add tests for mismatched lengths, generators, strings, NaN and infinity, non-positive entries, None lifetimes and duplicates.

KB-4 — Γ between 4/3 and about 1.4 is accepted, but the mass is already falling on the default grid

What happens
The accepted range is 4/3 < Γ ≤ 5, and the range is right for what it tests (a Newtonian polytrope is radially stable for Γ > 4/3). General relativity raises the threshold, so on the default TOV grid the mass of a Γ just above 4/3 is already falling at the high-density end. Measured on the default grid (n = 8, 1016 to 5 × 1019 kg m−3, pnuc = 0.04): Γ = 1.34 falls from 1.437 to 0.430 M☉ with no turning point; Γ = 1.40 has Mmax = 1.064 M☉ at 1.14 × 1017; Γ = 1.50 has 0.979 M☉ at 1.3 × 1018.
Classification
Documentation gap (Grok P3), not a code defect. The program warns that no turning point was found.
Suggested repair
One sentence in Beat 9 or EXP-17 saying that a TOV sequence can already be past its maximum on the default grid for Γ just above 4/3, so the turning-point warning is expected there.

KB-5 — The legend can hide the maximum-mass star (cosmetic)

What happens
Found while regenerating the SampleOutputs figures. On stiff sequences the legend of the mass–radius panel sits over the star that marks the maximum mass: partly hidden for the default polytrope (Figure 9 of the SampleOutputs guide), hidden for Γ = 3.0 (Figure 10). The maximum mass is still printed in the legend, in the summary and in the middle panel.
Workaround
Read the star from the middle panel, where the turning point is starred.

C. What Changed in 1.6.0 and 1.7.0

The full findings, with dispositions, are in Part F. This part lists what a user of 1.5.0 will notice.

Major improvements since 1.5.0

  • The Help is now a tutorial. Kickoff2 replaced the reference-text layout by the Beats layout: eleven beats (0–10), twenty experiments, and 22 equation blocks, each carrying exactly one of five tags: ODE, DERIVED, FIT, CLOSURE and PRESCRIPTION. A test reads every command the beats show, runs it through the real main.main(), and compares each quoted number with what the program prints (35 commands, 78 pairs).
  • The Chandrasekhar limit was corrected (1.7.0): the coefficient is derived from the n = 3 Lane-Emden solution and the module’s constants, 5.8252 / μe2, not typed as 5.836. MCh for μe = 2 is 1.4563 M☉ (was 1.459); the Newtonian neutron-gas limit is 5.726 (was 5.736; the Help says “about 5.73”). The program’s own structure integration converges to the new value.
  • Newtonian sequences are no longer given a maximum (1.6.0), because the extreme-density Newtonian peak is a step-size artefact. The program reports the largest sampled mass, says it is not a maximum, and counts the models whose radius is smaller than their own Schwarzschild radius.
  • The polytrope index is restricted to 4/3 < Γ ≤ 5 (1.7.0). Γ ≤ 6/5 has no finite surface; Γ ≤ 4/3 has no radially stable star. The error names the reason. (See KB-1 and KB-4 for what remains.)
  • Input validation is now uniform across the public API. One shared validator serves both equations of state; booleans, complex numbers (scalars and arrays) and non-finite values are refused; a 45-entry-point, 408-case matrix guards every numeric parameter; run() checks its four boolean controls and m_observed before doing any work.
  • The Mestel cooling assumption is stated and quantified (1.7.0): the matching layer at the degeneracy boundary is taken as envelope material, the core μe sets only the structure, and the alternative would make C 14.2 times smaller and the default cooling age 79.8 Gyr instead of 5.62.
  • The tests now include independent oracles (1.7.0): a separate Lane-Emden integrator, closed-form polytropes, the Chandrasekhar derivation, Sirius B, and measured second-order convergence for the white-dwarf and TOV integrators. The first thing they found was the 5.836 coefficient.

Release Status (1.5.0)

Version 1.5.0 concludes a kickoff regression-suite build followed by four rounds of independent review involving Claude, Codex, Copilot, and Gemini. The reviewers checked the stellar-evolution track, HR-diagram, white-dwarf cooling, and neutron-star mass–radius modes against their stated governing equations (homology relations and burning-law ODEs on the main sequence; core-mass–luminosity and Hayashi-line closures post-main-sequence; the exact Fermi-gas equation of state and Chandrasekhar structure for white dwarfs; the Tolman–Oppenheimer–Volkoff and Newtonian structure equations for neutron stars); verified remnant classification consistency across every output layer, numerical safeguards and input validation, output provenance and reproducibility, Help-file accuracy, Version/Build synchronization, and regression coverage; and tested both the canonical and flattened upload layouts. No release-blocking defect remains. Copilot and Gemini both recommended release after the Audit4 round with only previously disclosed, low-severity observations outstanding; Codex's one remaining reproducibility gap and three hardening items from that same round are fixed in this release, closing it with no open findings from any reviewer. The program is sufficiently robust, accurate, and clear for student use within the tutorial scope and limitations described below.

A second, independent series then started from scratch (Kickoff2, 19 September) and found further defects, all P1 and P2 of which were repaired in 1.6.0 and 1.7.0; two P2 and one P3 found by Audit23 remain open (Part B). Major Improvements in This Release (1.5.0)

  • Fixed a one-sided neutron-star turning-point check that could report a stable maximum mass from a sequence sampled entirely on one side of the true (unsampled) turning point; the check now requires an interior maximum on both sides, with distinct, actionable warnings for each one-sided failure.
    REPAIRED 1.2.0 Status update. The interior-maximum rule arrived in 1.2.0 and the neighbour-convergence rule in 1.3.0 (Audit2 A2-P2-6). Since 1.6.0 a Newtonian sequence never reports a turning point at all (Audit21 A21-P2-02). One boundary case remains open: KB-2 (a maximum at the lowest density sampled still gets a causality verdict computed from one model).
  • Fixed two related remnant-classification contradictions: a low-mass track's schematic outcome could disagree with what its own post-main-sequence integration actually computed, and "reached helium ignition" was being read from the wrong flag. A new remnant_basis field now threads a single, consistent story ("this track's own computed endpoint" versus "mass-only schematic classification") through the terminal summary, CSV comments, and plot annotations.
    REPAIRED 1.2.0 Status update. The helium-ignition flag and remnant_basis shipped in 1.2.0 and 1.3.0 (Audit1 P1-2, Audit2 A2-P1-1). The 1.7.0 samples show the wording in use: Figure 6 of the SampleOutputs guide is the 0.6 M☉ case.
  • Fixed a core-mass discontinuity at the main-sequence/post-main-sequence boundary for non-default --x_end values, so the post-main-sequence phase now begins continuously from the star's own last main-sequence state.
    REPAIRED 1.2.0 Status update. Audit1 P1-3.
  • Made wd_structure() raise an explicit, actionable error when its bisection search fails to converge, instead of silently returning an unconverged mass–radius pair; the search bracket now also widens adaptively so masses legitimately close to the Chandrasekhar limit succeed, and bracket-failure guidance is now side-specific (a too-small target mass gets different advice than one too close to the limit).
    REPAIRED 1.3.0 Status update. Adaptive bracket in 1.2.0 (Audit1 P2-1), the RuntimeError in 1.3.0 (A2-P1-2), side-specific advice in 1.4.0 (A3-P3-2). Known Limitations (1.5.0)

  • Intended for education and conceptual exploration of stellar-evolution and compact-object physics, not research-grade stellar modeling. Every mode is a deliberately simplified teaching model: main-sequence and post-main-sequence evolution use homology relations and empirical closures rather than a full stellar-structure integration; white-dwarf and neutron-star structure use idealized zero-temperature or ideal-gas equations of state; rotation, magnetic fields, mass loss, convective overshoot, and binary interaction are not modeled.
    BY DESIGN Unchanged. Sections 1.6.0 and 1.7.0 added measured statements of where each model is and is not adequate (validity table, Beats 6–10).
  • The schematic low-mass "helium white dwarf" remnant classification is a single-star mass-only heuristic; real helium white dwarfs at these masses generally require binary mass stripping to form, which this program does not simulate.
    BY DESIGN Since 1.6.0 the Help scopes the statement: helium white dwarfs of these masses are generally understood to be products of binary interaction, envelopes stripped early by a companion (Audit21 A21-P3-09).
  • The ideal degenerate neutron-gas equation of state (--eos neutron) supports at most about 0.7 solar masses—well under the roughly 1.4–2 solar masses of a typical measured neutron star—by design, so students can see degeneracy pressure alone is insufficient; the stiff-polytrope option is an illustrative stand-in for nuclear repulsion, normalized for pedagogical resemblance, not a fit to microscopic nuclear matter or observations.
    BY DESIGN Unchanged: the 1.7.0 sample (Figure 8) gives 0.7100 M☉ at 9.313 km. The polytrope side of this limitation gained one more caveat, KB-1.
  • Turning-point detection in the neutron-star mass–radius sequence requires an interior sampled maximum; it does not perform local slope-sign-change refinement or interpolation, so the reported maximum mass is only as precise as the sampling grid.
    OPEN Still true. Since 1.6.0 the rule is stated only for TOV sequences (a Newtonian sequence is never classified), and one boundary case is a known bug (KB-2). The fuller slope-sign-change criterion was declined in Audit1 and Audit2 and has not been reopened.
  • No independent, externally published white-dwarf mass–radius benchmark comparison is included. Internal consistency checks (the Chandrasekhar-mass asymptote, non-relativistic scaling laws) are extensive, but this remains a validation opportunity rather than a demonstrated defect.
    PARTLY ADDRESSED 1.7.0 The suite now contains independent references written outside the program: a separate Lane-Emden integrator, closed forms for n = 1 and 3, the Chandrasekhar-mass derivation, and Sirius B (model radius 5583 km at 1.018 M☉, inside 2 per cent of the published 5634 km). That exercise found the 5.836 coefficient error. There is still no comparison with a published white-dwarf mass–radius table or a modern cooling sequence.
  • Same-second output-collision protection (CSV, PNG, and their provenance sidecars) is deterministic and effective within one running program, but there is no stronger cross-process atomic-exclusive-create guarantee against two independent processes racing to create the same filename; no exercise in this program depends on concurrent processes sharing an output directory.
    OPEN Unchanged. Re-raised by Copilot in Audit4 and restated in Audit21 and Audit22; accepted as a documented limitation each time.
  • Scientific-model narrative (remnant-basis wording, provenance phrasing) is intentionally worded consistently but duplicated across several consumer layers (terminal output, CSV/PNG provenance, the Help file) rather than centralized in one shared template, which aids transparency and auditability at some future maintenance risk if one layer is edited without the others.
    OPEN Unchanged. Since 1.7.0 the statements that have already drifted are guarded by TestHelpClaimsAgreeAcrossLayers (12 tests: each changed claim is asserted in every layer that makes it, and the old wrong wording is asserted absent). Centralising the text was considered and not done (Audit22 Copilot P2-03).
  • The .py.txt transport-encoded companion files shipped alongside each delivered source file are a packaging aid only, meant to survive Markdown-oriented rendering pipelines during review; they are never meant to be executed and are not part of the program.
    NOT APPLICABLE SINCE KICKOFF2 The companions are no longer shipped.
  • The Help file loads MathJax from a public CDN. Offline, its prose and unrendered TeX source remain available, but equations are not typeset; this has no effect on the program itself, which needs no internet access to run.
    OPEN Unchanged.
