Description

BlackHoleShadow answers one question that PhotonOrbit and GravitationalLensing each leave for the other to answer: what does a camera actually record when it points a whole grid of directions at a black hole? PhotonOrbit already classifies a single Schwarzschild photon by its impact parameter \(b\); GravitationalLensing already maps a whole source plane onto an image plane for a transparent lens. Neither program launches a bundle of photons into a camera and asks which directions on the sky come back dark. This one does.

The spine of the lesson is one sentence: the silhouette a camera records is an image-plane set of captured directions, bounded by the critical curve \(b_{\rm crit}=3\sqrt3\,M\) — not the coordinate circle \(r=2M\), and not a thin-lens Einstein ring. Nine modes, selected with --mode, build that sentence up one piece at a time: two rays, a coarse pixel grid, a dense capture map, a highlighter for the near-critical rays that wind around before escaping, the radii at which a face-on emitting ring crosses each ray, a false-colour image built from those crossings, a reminder that a coordinate radius and an image-plane radius are not the same axis, the large-\(b\) limit of the deflection, and a direct comparison against a transparent galaxy's Einstein ring.

What this program is, and what it is not. Every ray in every mode is an exact null geodesic of the vacuum Schwarzschild metric, integrated or quadrated to the precision utilities_bhs.py asks for near the critical impact parameter. It is not a Kerr movie: there is no spin. It is not an Event Horizon Telescope pipeline: there is no interferometry, no scattering screen, no plasma. It is not a fluid or radiative-transfer simulation: mode image is a face-on, optically thin toy (Gralla, Holz & Wald 2019), and there is no inclination — --inclination accepts only \(0\) and refuses anything else, because a correctly inclined image needs a three-dimensional camera/disk geometry this program does not build. It is not PhotonOrbit with a slider: PhotonOrbit's object is one ray's accumulated azimuth; this program's object is a whole grid of rays and the boundary between the ones that come back and the ones that do not. And it is not GravitationalLensing with \(M\) turned up: a thin-lens kink \(\boldsymbol\alpha=\theta_E^2\boldsymbol\theta/|\boldsymbol\theta|^2\) has no critical null geodesic in it and cannot produce a shadow, which is the whole content of Beat 8.
False colour, always. Mode image paints a scalar intensity with the inferno colormap. That colour is a display scale for a single bolometric number, not the spectrum of the source. Gravitational deflection here is achromatic: nothing in this program bends blue light differently from red. A palette was chosen only so a faint ring is visible on a screen.
Reading this page. Equations are rendered by MathJax, loaded from a public CDN, so an internet connection is needed to see them typeset; offline, the raw \(\LaTeX\) source shows as plain text. The program itself needs no internet access to run. A blue DERIVED tag marks an equation obtained by exact reasoning from the Schwarzschild metric and geometric optics — almost everything on this page. A grey PRESCRIPTION tag marks a rule the program adopts rather than derives: there is exactly one, the high-winding threshold of Beat 3. Unlike StellarEvolutionTracks, there are no fits, no calibrated closures and no integrated evolution equations here — the physics is a single exact metric, and the tagging system has correspondingly little work to do. That is itself worth noticing: not every program in this suite needs the same scaffolding, and forcing a five-way taxonomy onto a program with only one kind of ingredient would be decoration, not honesty.

Before the first run

Unpack the program zip so you have a folder named BlackHoleShadow containing main.py, and open a terminal there. You need Python 3.10 or newer with NumPy, Matplotlib, SciPy and mpmath (see requirements.txt); SciPy handles ordinary ray quadrature and mpmath takes over at the working precision set in utilities_bhs.MP_DPS whenever \(b\) sits close enough to \(b_{\rm crit}\) that ordinary floating point can no longer be trusted. If you do not already have that environment, follow the project-wide GFTGUX Python Setup Guide, and do not install packages into a system Python (PEP 668). Then:

python main.py --version
python main.py --mode rays

Every command on this page assumes that working directory. Lengths are in units of \(M=GM/c^2\); the teaching default is \(M=1\), so a length written as 5 on the command line means \(5M\). Even values of --n_pix are rounded up to the next odd number, so a pixel always sits exactly on the optical axis; there is no --csvdir option in this program — unlike StellarEvolutionTracks, no mode produces a table of rows meant for a spreadsheet, only a figure and, optionally, a saved PNG.

How to read this page

Each numbered section below is one beat: a short argument, a command whose figure is the evidence, and then the equation the figure has earned. Do them in order the first time; the modes build on each other in exactly the order the nav bar lists them, and the program's own figure titles carry the same beat numbers you will see here. After the first pass, any beat can be opened on its own.

This program has far less internal machinery than StellarEvolutionTracks: one metric, one first integral, nine ways of asking a question about it. The beats are correspondingly about where a familiar quantity lives — on the sky, in a coordinate, in a source plane — more often than they are about a new equation.

Beat 0 · Two rays, one first integral

PhotonOrbit has already classified a single Schwarzschild photon by its impact parameter \(b\). This beat repeats exactly that classification, with exactly the same first integral, so that the camera grid built in the rest of this program is visibly the same physics and not a new metric in disguise.

python main.py --mode rays
Null first integral (\(E=1\), \(L=b\)) DERIVED
\[\left(\frac{dr}{d\lambda}\right)^{2}=1-\left(1-\frac{2M}{r}\right)\frac{b^2}{r^2},\qquad b_{\rm crit}=3\sqrt3\,M.\]

Three tasks, in order. First read the console: at the default \(b=5M\) the ray is reported captured, and at \(b=6M\) it is reported escaped, with \(b_{\rm crit}/M=5.19615\) printed on the line above. Then read the two \(\Delta\phi\) values, 4.50174 and 4.63537 radians for the captured and escaping ray respectively, and notice that neither number is obviously special — 4.502 is not \(\pi\), and 4.635 is not the deflection angle of anything. Then look at the figure: the red curve at \(b=5M\) runs to the horizon \(r_s=2M\) and stops; the blue curve at \(b=6M\) turns around outside the photon sphere and heads back out.

Then the distinction that the rest of this program depends on. \(\Delta\phi\) is the azimuth accumulated to a finite stopping surface — the horizon for a captured ray, or twice the camera radius for an escaping one — exactly as PhotonOrbit reports it. It is not the asymptotic deflection angle \(\hat\alpha\) that a distant observer would measure; that quantity needs the ray followed all the way to infinity, which is Beat 7's subject, and it is a different number from either \(\Delta\phi\) printed here. Keeping the two apart is not pedantry: \(\hat\alpha\) diverges as \(b\to b_{\rm crit}^+\), while \(\Delta\phi\) to a finite camera does not, and mistaking one for the other is the most common way a student misreads the console output of this program.

Beat 1 · A ray becomes a pixel

The only new object between Beat 0 and here is the camera itself: a map from a two-dimensional grid of impact-parameter pairs \((b_x,b_y)\) to one of two labels, captured or escaped. Nothing about the differential equation has changed; what has changed is that you are now looking at a picture of a classification rather than a single trajectory.

python main.py --mode pixels

The figure is a coarse \(17\times17\) grid, deliberately too coarse to look like a shadow yet. Find the cell nearest \(b=5M\) and the cell nearest \(b=6M\): one is dark, one is light, and they are the same two rays from Beat 0, now expressed as directions on a sky rather than as trajectories in a side view. --n_pix in this mode is capped at 41, and the program says so on the console if you ask for more, because the point of pixels is to make individual cells visible, not to anticipate capture.

Then the idea the rest of the program builds on: a camera does not record trajectories, it records a function of direction. Every later mode is a denser, cleverer, or more physically dressed version of exactly this map.

Experiments that go with this beat: EXP-2 in Suggested Experiments.

Beat 2 · The geometric shadow

Make the same grid dense and the picture becomes recognisable: a dark disk on a light background. The question this beat exists to settle is where its rim actually sits.

python main.py --mode capture
python main.py --mode capture --fov 24 --n_pix 201

Read the console. At the defaults, 8469 of 25921 pixels are captured, on a \(161\times161\) grid spanning a field of view of \(16M\); the summary also prints \(b_{\rm crit}/M=5.19615\), the horizon \(r_s/M=2\) and the photon sphere \(r_{\rm photon}/M=3\) on the same block, so the three numbers sit next to each other on purpose. The second command, at \(24M\) field of view and a finer \(201\times201\) grid, captures 5901 of 40401 pixels — a smaller fraction, because the field of view grew while the shadow did not.

Three tasks, in order. First confirm the shadow's angular size does not depend on the field of view you chose: divide captured pixels by total pixels in each run and multiply by (field of view)\(^2\), and compare the two results — they should agree to within the grid's own resolution, since both are estimating the same disk of radius \(b_{\rm crit}\). Then find BlackHoleSpacetimeVisualizer's own diagrams, which draw the horizon \(r_s=2M\) as a circle in an embedding or a coordinate plot; that circle is not drawn anywhere on this page, on purpose. Then explain, in one sentence, why not: what coordinate is the horizontal axis of this figure, and is it the same coordinate as the horizontal axis of one of BlackHoleSpacetimeVisualizer's diagrams?

Then the answer, precisely. Every pixel on this grid is a value of the impact parameter \(b\), a constant of motion measured at infinity (or, for a finite camera, an angle converted to that same constant — Beat 7 makes that conversion explicit). The rim of the dark disk sits at \(b=b_{\rm crit}=3\sqrt3\,M\approx5.196\,M\), not at \(r=2M\) and not at \(r=3M\). Those two coordinate radii belong to a different axis entirely — Beat 6 puts both axes on the same page so the difference cannot be missed twice.

A resolution floor, not a resolution claim. The program refuses a grid on which the shadow diameter \(2b_{\rm crit}\) spans fewer than eight pixel intervals; asking for --fov 80 --n_pix 11 is refused with the shadow diameter 2 b_crit = 10.39 M spans only 1.30 grid intervals. That floor exists so a run cannot silently draw a shadow no wider than a handful of pixels and call it resolved. It is not a claim about what angular resolution a real telescope needs to see a real shadow.

Beat 3 · A highlighter, not a photon ring

Three names get run together constantly in popular accounts of black-hole imaging, and this beat exists to keep them apart before doing anything else with them.

  • The photon sphere is a place in spacetime: the coordinate locus \(r=3M\), where a circular photon orbit is (unstably) possible.
  • The critical curve is a place on the sky: the image-plane circle \(b=b_{\rm crit}\), the rim of the dark disk from Beat 2.
  • A photon ring is a feature of a picture: a bright, narrow image that appears near the critical curve only when there is emitting matter to send high-order rays to the observer. No matter, no photon ring — the vacuum alone produces only the first two.
python main.py --mode ring

Read the console: the high-winding window is \((5.19615,\,5.27716]\,M\), a band only about 1.6% wide in \(b/M\), and 256 pixels of the \(161\times161\) grid fall inside it. Look at the figure: an orange band sits just outside the dark disk's rim, hugging the critical curve. That band is not a photon ring — this program has no emitting matter in mode ring at all — it is a highlighter on escaping rays whose periapsis lands within \(0.35M\) of the photon sphere and whose accumulated azimuth exceeds \(2\pi\): rays that wind more than once around the hole before finally escaping. Those are exactly the near-critical whirling rays PhotonOrbit already demonstrates for a single trajectory; this mode paints the same phenomenon as a set of directions on the sky instead of as one curve in a side view.

High-winding overlay window PRESCRIPTION
\[b_{\rm lo}=b_{\rm crit},\qquad b_{\rm hi}=\text{largest }b\text{ with periapsis within }0.35M\text{ of }3M\text{ and }\Delta\phi_\infty>2\pi.\]

Both thresholds — the \(0.35M\) window around the photon sphere and the \(2\pi\) winding requirement — are educational choices, tuned to make a visible band on a typical grid, not measurements of any physical width. Nothing about a real photon ring's brightness or thickness follows from where this program draws its highlighter.

Then the sentence worth keeping: the shadow rim in Beat 2 is PhotonOrbit's critical capture/escape boundary painted onto a sky; the highlighter in this beat is PhotonOrbit's near-critical whirling demonstration painted the same way. Nothing here is new physics — it is the same one first integral, looked at from a camera's point of view three times in a row.

Beat 4 · Transfer functions \(r_m(b)\)

Give the hole a face-on observer at infinity and a thin, flat, equatorial emitting plane, and every impact parameter \(b\) becomes a label for a null geodesic that crosses that plane one or more times as it orbits and either escapes or falls to the horizon. The radii of those crossings, as functions of \(b\), are the transfer functions this beat exists to compute.

python main.py --mode transfer

Read the console: for the default hot-ring radius \(r_{\rm hot}=6M\), the three transfer functions equal \(r_{\rm hot}\) at \(b/M=6.9321\), \(5.4789\) and \(5.208\) respectively — three different impact parameters, converging toward \(b_{\rm crit}=5.19615\) as the crossing order rises. That convergence is the whole geometric content of a photon ring: higher-order crossings are squeezed into an ever-narrower band of \(b\) just outside \(b_{\rm crit}\).

Three tasks, in order. First identify \(m=1\): the direct image, one crossing per ray, the ordinary case. Then identify \(m=2\): the "lensing ring" crossing, a second pass through the disk plane on the far side of the hole. Then note that a captured ray (\(b\le b_{\rm crit}\)) only ever travels inbound — it cannot loop back out — but it can still cross the disk plane once on its way to the horizon; the program's own integrator stops such a ray exactly at \(r=2M\), so a captured ray's crossing, if any, is always found before that stop.

Then the count: this program computes \(m\) up to 4 and no further. Read the console line again — finite \(r_3\) samples: 110 out of 192 adaptively placed \(b\) values — and notice that not every sampled \(b\) has a well-defined third crossing at all; some rays simply do not pass the disk plane a third time within the domain the program searches. \(m\ge5\) is not a rounding choice: the program does not compute it, at any \(b\), because the higher orders contribute a vanishingly small share of any realistic image's flux and because each additional order needs the arbitrary-precision machinery of utilities_bhs.py over an ever-narrower range of \(b\).

Beat 5 · A face-on optically thin image

Give the transfer functions of Beat 4 an emitted intensity profile and a redshift factor, and a genuine picture appears: not just where a ray crosses the disk, but how bright that crossing looks to the distant observer.

Optically thin face-on image DERIVED
\[I_{\rm obs}(b)=\sum_{m=1}^{4}g(r_m)^4\,I_{\rm em}(r_m),\qquad g(r)=\sqrt{1-\frac{2M}{r}}.\] 
python main.py --mode image
python main.py --mode image --r_hot 8

The emitted profile \(I_{\rm em}\) is a Gaussian annulus centred on \(r_{\rm hot}=6M\) with width \(0.45M\); it is an invented teaching source, not a measured one, and the program says so on the console. Read the redshift factor at the annulus: \(g(6M)^4=0.444444\) exactly, since \(g(6M)^2=1-2/6=2/3\) and \((2/3)^2=4/9\). Three panels are drawn: direct only (\(m=1\)), plus the lensing-ring crossing (\(m\le2\)), and plus the photon-ring/subring crossings (\(m\ge3\)).

Three tasks, in order. First read the console's max table I_2 / I_m=3,4 line — 0.4457 for the lensing-ring peak and, separately, 0.4457 for the combined \(m=3,4\) peak in the adaptively sampled table — and notice the two peak heights are comparable even though the higher-order image occupies a vastly narrower range of \(b\); a peak's height alone does not tell you its share of the total flux. Then read max raster m>=3 increment: 0.07043, the largest \(m\ge3\) contribution the fixed pixel raster itself actually samples, and compare it with the table's 0.4457 — the raster undershoots badly, because a grid of pixel centres has no reason to land inside a band only a few thousandths of \(M\) wide in \(b\). Then look at the radial \(I(b)\) panel beneath the images, which is drawn from the adaptively placed table rather than the raster, and find the narrow spike the 2-D image itself is too coarse to show.

Then the two disclaimers that keep this mode from being mistaken for something it is not. There is no orbital Doppler: \(g\) here is gravitational redshift only, for a static emitter, not an emitter orbiting the hole, which is why the console calls these "static emitters" explicitly. And a captured ray traced backward from the camera crosses the event horizon and stops there — the integrator halts at \(r=2M\) — so if that inbound ray would have crossed the disk plane only after passing through the horizon, this program cannot and does not report that crossing; it may still find an earlier one before the horizon, which is exactly what the console's closing note describes.

Beat 6 · Coordinate radii are not image-plane radii

This beat introduces no new physics at all. It exists because Beats 2 and 4 have now both used the symbol "radius" for two different things, and conflating them is the single easiest mistake to make with this program's output.

python main.py --mode radii

Two panels, side by side. The left panel is a Schwarzschild coordinate-radius cross-section: a number line marked at the horizon \(r_s=2M\) and the photon sphere \(r_{\rm ph}=3M\). It is not a spacetime diagram and it draws no light rays. The right panel is the image plane: the same critical curve \(b_{\rm crit}\approx5.196\,M\) from Beat 2, and nothing else — deliberately, \(r_s\) and \(r_{\rm ph}\) are not drawn there, because they are coordinate radii and this is not a coordinate-radius axis.

The task: point to the circle on the right panel and say which quantity from the left panel it does not equal. It is close in value to \(r_{\rm ph}=3M\) times \(3\sqrt3/3=\sqrt3\approx1.73\), which is not a coincidence — \(b_{\rm crit}\) is derived from the condition that a photon orbit exists at \(r=3M\) — but "derived from" is not "equal to," and a finite real camera at radius \(r_{\rm cam}\) would measure a local angle related to \(b\) by a factor that depends on \(r_{\rm cam}\) itself, which Beat 7's experiments make explicit.

Beat 7 · The same ray, far away

Beat 0 drew a firm line between \(\Delta\phi\), the azimuth accumulated to a finite camera, and \(\hat\alpha\), the deflection a distant observer would actually measure. This beat computes \(\hat\alpha\) properly and shows that it is nothing more than the same first integral, evaluated all the way to infinity.

Weak-field light deflection DERIVED
\[\hat\alpha=\frac{4GM}{c^2b}=\frac{4M}{b}\qquad(b\gg M).\] 
python main.py --mode weak

Read the console at the two sampled points nearest each end of the curve. At \(b=41.6M\), far from the hole, the exact and weak-field deflections agree closely: 0.1037 rad exact against 0.096225 rad from \(4M/b\), a difference of about 7%. At \(b=5.3M\), just outside \(b_{\rm crit}=5.196M\), they have come completely apart: 3.5572 rad exact against 0.75471 rad weak-field, the exact value now almost five times larger. Three tasks, in order. First compute \(4M/b\) by hand at both points and confirm the console's weak-field column. Then compute the relative error of the weak-field formula at each point and confirm it grows sharply as \(b\to b_{\rm crit}^+\). Then say, using only the phrase "strong deflection," what is physically happening to a ray whose exact \(\hat\alpha\) exceeds \(\pi\) — such a ray has wound more than halfway around the hole before escaping to infinity.

Then the connection back to Beat 3: this divergence as \(b\to b_{\rm crit}^+\) is exactly what makes higher-order images possible when a source supplies photons to bend. It is the mechanism behind a photon ring, not a photon ring by itself — there is still no emitting matter anywhere in this mode.

Beat 8 · Two rings, two meanings

GravitationalLensing's Einstein ring and this program's critical curve are both circles with a formula and a name, and the two names get used interchangeably in casual conversation about "gravitational rings." They are not the same object, and this beat exists to put the two numbers on one page so the difference cannot be waved away.

python main.py --mode compare
python main.py --mode compare --logM 12.5

Read the console: for the default \(10^{12}\,M_\odot\) transparent point-mass galaxy, at GravitationalLensing's cartoon distances \(D_l=1\,{\rm Gpc}\), \(D_s=2\,{\rm Gpc}\), the Einstein radius is \(\theta_E=2.018''\), and that same radius measured in units of the galaxy's own gravitational length \(GM/c^2\) is \(R_E/M\approx2.044\times10^5\) — about two hundred thousand gravitational radii. Raise the mass to \(10^{12.5}\,M_\odot\) and \(\theta_E\) grows to \(3.588''\) while \(R_E/M\) actually shrinks, to about \(1.150\times10^5\): a bigger mass at fixed distances subtends a larger angle on the sky but, because \(R_E\) scales as \(\sqrt M\) while the gravitational length scales as \(M\), the ring sits at fewer and fewer gravitational radii as the lens gets heavier.

Set that against this hole's own numbers, unchanged by any of the above: the photon sphere is at \(r_{\rm ph}=3M\) and the image-plane critical curve is at \(b_{\rm crit}\approx5.196\,M\) — five and a bit gravitational radii, full stop, for a black hole of any mass, because the Schwarzschild metric is scale-invariant in units of \(M\). A weak-field galaxy lens sits at a hundred thousand or more gravitational radii from its own centre; a black hole's critical curve sits at about five. That factor of \(10^4\)–\(10^5\) is the entire content of "one is a weak-field ring, the other is a strong-field one," made numerically explicit rather than asserted.

Then the reason no thin lens can do what this program does. GravitationalLensing's deflection law \(\boldsymbol\alpha=\theta_E^2\boldsymbol\theta/|\boldsymbol\theta|^2\) is a first-order, small-angle approximation: it bends a ray once, at one plane, by an amount that stays finite everywhere except the lens's own singular point. It has no mechanism for a ray to wind around a centre indefinitely, because it was built by throwing away exactly the higher-order terms that would let it. The critical null geodesic that rims a black-hole shadow is intrinsically a strong-field object, and producing it requires integrating the full metric, which is the whole reason this program and GravitationalLensing had to be two separate programs rather than one with a bigger mass.

Algorithm

Modes rays and pixels

  1. Validate \(M\), the camera radius (must exceed \(3M\)), and the two demonstration impact parameters.
  2. Classify each \(b\) against \(b_{\rm crit}=3\sqrt3\,M\): captured if \(b\le b_{\rm crit}\), escaped otherwise. Equality is treated as captured, a set of measure zero on any grid.
  3. For rays, integrate \(\left(\frac{dr}{d\lambda}\right)^2=1-(1-2M/r)(b/r)^2\) outward or inward from the camera with fixed-step RK4, stopping at the horizon, at the affine budget --lambda_max, or when the ray has travelled twice the camera radius outward.
  4. For pixels, snap the two demonstration impact parameters to the nearest cell centre of a coarse grid (default \(17\times17\), capped at \(41\times41\)) and classify every cell.

Mode capture

  1. Build a square grid of \((b_x,b_y)\) pairs spanning --fov on a side, at the requested (odd-rounded) --n_pix.
  2. Refuse the grid outright if the shadow diameter \(2b_{\rm crit}\) would span fewer than eight grid intervals — a visibility floor, described in Beat 2.
  3. Classify every pixel by \(b=\sqrt{b_x^2+b_y^2}\) against \(b_{\rm crit}\), vectorised over the whole grid at once.

Mode ring

  1. Compute the same dense capture map as capture.
  2. Find the high-winding window \((b_{\rm crit},\,b_{\rm hi}]\) by a bisection search in \(\log(b/b_{\rm crit}-1)\): a candidate \(b\) qualifies if its periapsis lies within \(0.35M\) of the photon sphere and its accumulated escaping azimuth exceeds \(2\pi\).
  3. Root-find the periapsis of every escaping ray needed by that search; ordinary Newton iteration is used away from \(b_{\rm crit}\), and the program switches to a perturbative expansion, then to mpmath at the working precision in utilities_bhs.MP_DPS, as \(b\) approaches \(b_{\rm crit}\) closely enough that double precision can no longer resolve the difference \(b-b_{\rm crit}\).
  4. Refuse a grid too coarse to resolve the resulting window by at least half a pixel interval.

Modes transfer and image

  1. Build an adaptively spaced table of \(b\) values, clustered logarithmically on both sides of \(b_{\rm crit}\) (near) and spread more coarsely elsewhere (far), so the near-critical crossings are actually resolved rather than skipped by a uniform grid.
  2. For each sampled \(b\), find every crossing of the equatorial plane up to \(m=4\) by inverting the accumulated-azimuth integral at the disk-plane angles \(\pi/2,\,3\pi/2,\,5\pi/2,\dots\), using the same near-critical switch to mpmath described above.
  3. For image, evaluate the emitted Gaussian-annulus profile and the redshift factor \(g\) at each found crossing radius, sum \(g^4I_{\rm em}\) over the available crossings, and separately build a source-aware table (used for the radial \(I(b)\) panel) and a fixed pixel raster (used for the 2-D image), so that narrow high-order peaks the raster would miss are still visible in the radial panel.

Mode weak

  1. Sample 48 values of \(b\) geometrically between \(1.02\,b_{\rm crit}\) and \(8\,b_{\rm crit}\).
  2. At each, quadrate the exact asymptotic deflection integral (the standard \(u=1/r\) substitution) and separately evaluate \(4M/b\).

Mode compare

  1. Evaluate the point-mass Einstein-radius formula for the requested galaxy mass at GravitationalLensing's fixed cartoon distances \(D_l=1\,{\rm Gpc}\), \(D_s=2\,{\rm Gpc}\).
  2. Convert to arcseconds and to units of the galaxy's own gravitational length \(GM/c^2\); report both beside this hole's fixed \(b_{\rm crit}/M\) and \(r_{\rm ph}/M\).
Precision safeguard, stated plainly: every calculation in this program that depends on \(b-b_{\rm crit}\) — periapsis, asymptotic deflection, the high-winding window, the transfer functions near \(m\ge2\) — is vulnerable to catastrophic cancellation in ordinary double precision as \(b\) approaches \(b_{\rm crit}\), because the two quantities being subtracted agree to more digits than a 64-bit float can hold. utilities_bhs.py exists specifically to detect when a calculation has entered that regime and switch to arbitrary-precision arithmetic (mpmath, at a working precision of MP_DPS decimal digits) rather than silently return a number that looks plausible but is not. This is why the ring and transfer/image modes are noticeably slower than capture: they are doing real extra-precision work exactly where the ordinary floating-point calculation would quietly fail.

Module Overview

Physics Layer
physics_bhs.py

Constants, the null first integral, capture classification, periapsis and asymptotic-deflection root-finding and quadrature, the high-winding window, the transfer-function and disk-image machinery, and the galaxy-comparison formulae. All validation of physical inputs lives here.

Precision Layer
utilities_bhs.py

Arbitrary-precision (mpmath) evaluation of the near-critical quantities that ordinary double precision cannot resolve, at a fixed working precision MP_DPS; also the Dekker-split double-double helpers used to detect when a value is close enough to \(b_{\rm crit}\) to need that switch.

Driver Layer
driver_bhs.py

Dispatches on --mode, builds each mode's grid or sample table, prints the run summary, and calls the plotter. No CSV output; a run produces a figure and, optionally, a saved PNG.

Plot Layer
plot_bhs.py

Nine figure layouts, one per mode, each titled with its own beat number so a saved plot and this Help file always agree on which beat it illustrates. With --outdir, also saves a timestamped PNG and a same-stem .provenance.txt sidecar recording the version, build, and the run's parameters.

Entry Point
main.py

Defines the student-facing command-line options, grouped by purpose, and converts validation or runtime failures into concise command-line error messages.

Parameters

Run python main.py --help for the current command summary, and python main.py --version for the model version, which every saved figure's footer also repeats. Options that do not apply to the selected mode do not change its results, but several are validated regardless of mode, so an out-of-range value is refused even where it would not otherwise have been used.

Suggested Experiments

Nothing here needs anything beyond the program itself and the printed console summary. The exercises run from reading the output through controlled comparisons to a little numerical judgement; nothing in this program needs curve fitting or calibration, because — unlike StellarEvolutionTracks — there is nothing here that was calibrated in the first place.

Introductory

EXP-1

Capture versus Escape

Run --mode rays at the defaults, then again with --b_in 5.19 --b_out 5.21. Name the status of each ray from the console before you look at the figure, then check yourself against \(b_{\rm crit}/M=5.19615\). Notice how much larger \(\Delta\phi\) has become for both rays compared with the default run, and connect that to Beat 3's "winding" language.

EXP-2

A Pixel Is a Direction

Run --mode pixels. Point to the dark cell and the light cell and state, in one sentence each, which trajectory from --mode rays each one represents.

EXP-3

The Rim Is Not the Horizon

Run --mode radii. The left panel is a coordinate-radius cross-section; the right panel is the image plane. Which circle on the right matches the dark disk of --mode capture, and why are \(r_s\) and \(r_{\rm ph}\) not drawn there at all?

EXP-4

PhotonOrbit on the Sky

The shadow rim of Beat 2 is PhotonOrbit's critical capture/escape ray. The highlighter of --mode ring is PhotonOrbit's near-critical whirling ray, painted as a set of directions instead of one trajectory. Run both programs side by side and write, in your own words, what has changed and what has not between the two ways of showing the same physics.

Intermediate

EXP-5

Recover \(4M/b\)

From the --mode weak console line, compute the relative error of \(4M/b\) at the largest sampled \(b\) (41.6\(M\)) and at the smallest (5.3\(M\)). By roughly what factor does the error grow between the two? Then argue, from the form of the exact first integral in Beat 0, why the error has to grow as \(b\to b_{\rm crit}^+\) rather than staying small.

EXP-6

Two Rings, Two Meanings

Run --mode compare at --logM 10, 12 and 14, and tabulate \(\theta_E\) and \(R_E/M\) for each. Confirm that \(\theta_E\) grows with mass while \(R_E/M\) shrinks, and explain the two different scalings (\(\sqrt M\) against distances that do not change, versus a length compared with a gravitational scale that itself grows as \(M\)) that together produce that split behaviour. Then write one sentence, using the word "ring" only once, that keeps the galaxy's Einstein ring and this hole's critical curve from being confused.

EXP-7

Achromatic Silhouette

Run --mode image. The palette is inferno. Write down what would change in the figure if the emitting annulus radiated at a different wavelength. (Nothing in the capture map would.) Then compare the three image panels and, for each, say which transfer-function crossing is responsible for the light in it.

EXP-8

Finite Camera

Rerun --mode rays with --r_cam 10 and then --r_cam 80, and read \(\Delta\phi\) for both rays each time. The capture/escape classification does not change with \(r_{\rm cam}\) — it cannot, since it depends only on \(b\) versus \(b_{\rm crit}\) — but \(\Delta\phi\) does. A static observer at finite \(r\) measures a local emission angle \(\alpha\) related to \(b\) by \(\sin\alpha=(b/r)\sqrt{1-2M/r}\); use it to explain why the same ray looks different to cameras at different radii even though its classification never changes.

Advanced

EXP-9

The Resolution Contract

Try --mode capture --fov 80 --n_pix 11 and read the refusal message carefully: it states the shadow's angular span in grid intervals and the reason for the floor. Then find the smallest --n_pix (not exceeding 81) that satisfies the eight-interval rule at --fov 80, and confirm your answer by running it.

EXP-10

Where the Source Images Sit

Run --mode transfer and read the three crossing impact parameters for \(r_{\rm hot}=6M\). At the \(b\) where the direct-image peak in --mode image's radial panel sits, confirm \(r_1\approx r_{\rm hot}\) from the transfer-function table. Then, at a \(b\) only slightly larger than \(b_{\rm crit}\), count how many of the four transfer functions this program actually computes are defined there, and explain from Beat 4 why the count does not keep rising as \(b\to b_{\rm crit}^+\) even though, physically, a ray infinitesimally outside \(b_{\rm crit}\) can cross the disk plane arbitrarily many times.

Synthesis

EXP-11 · synthesis

One Metric, Nine Questions

Make a table with one row per mode and three columns: the quantity that mode computes, the beat that earns it, and the one sentence that mode exists to prove wrong if a student conflated it with something else (a horizon, a photon ring, a thin-lens ring, an inclined disk, a chromatic image). Then write, in no more than three sentences, what this program adds that PhotonOrbit and GravitationalLensing together do not already provide — and be honest about how much of that addition is a new calculation versus a new way of displaying an old one.

Domain of Validity

  • Schwarzschild only, vacuum, geometric optics. No spin, no charge, no plasma, no accretion-flow radiative transfer. Every ray is an exact null geodesic; nothing here is fitted, calibrated, or approximated except where a beat says so explicitly (the weak-field formula of Beat 7, by construction).
  • The capture map is a geometric idealisation. Calling the dark disk of Beat 2 a "shadow" assumes a distant, nearly uniform bright screen behind the hole. A real thin emitting disk produces a different central depression, with its own transfer functions — that is exactly what mode image computes instead, and the two should not be read as the same calculation.
  • Mode image is a face-on, optically thin toy (Gralla, Holz & Wald 2019), with an invented emissivity profile. It is not an Event Horizon Telescope reconstruction, not a Kerr calculation, and not a fluid simulation. Subrings narrower than a pixel can miss every raster cell; the radial \(I(b)\) panel, built from the adaptive table rather than the raster, is the honest record of those peaks.
  • No inclination. --inclination accepts only 0. A correctly inclined image needs a genuinely three-dimensional camera/disk geometry this program does not build; adding it is future work, not a parameter this version silently mishandles.
  • PhotonOrbit's \(\Delta\phi\) remains accumulated azimuth to a finite stopping surface, never the asymptotic deflection \(\hat\alpha\). The curve in --mode weak is \(\hat\alpha\), computed by quadrature of the same first integral, not read off any finite-camera \(\Delta\phi\).
  • Compare-mode distances are GravitationalLensing's cartoon \(1\,{\rm Gpc}/2\,{\rm Gpc}\), chosen so Einstein radii come out in arcseconds for a teaching example. They are not a cosmological model and should not be read as one.
  • Near-critical precision is real work, not free. Ring, transfer and image modes are slower than capture because they are switching to arbitrary-precision arithmetic exactly where an ordinary float would silently lose accuracy; there is no shortcut around that cost if the near-\(b_{\rm crit}\) numbers are to be trusted at all.
